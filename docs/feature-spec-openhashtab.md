# 功能规格说明：基于 OpenHashTab 分析的核心功能清单

## 0. 第一性原理立场

1. **只读一遍**：文件 IO 是吞吐瓶颈，对同一次读取的字节流并行喂给所有目标算法，避免重复读盘。
2. **内存有界**：并发在途数据量必须设上限，否则批量大文件会 OOM（资源是有限的）。
3. **引擎与界面解耦**：哈希计算的正确性不依赖任何 UI；UI 只是结果的订阅者与指令的发布者（关注点分离）。
4. **可信边界**：非加密哈希（CRC/XXH/MD5/eD2k…）不应被误用于完整性/安全校验场景，需显式标注"不安全算法"以防止误用。
5. **格式嗅探优于格式选择**：用户手里的校验文件格式不统一，工具应自动识别 hex/sfv/base64，而非强制用户选格式。
6. **状态必须可区分**：match / mismatch / insecure / error 四态语义独立，配色一一对应，让用户在结果区一眼判断。
7. **设置集中且可持久**：算法开关、展示偏好、导出格式、外部声誉同意等需集中管理并跨会话保留（用配置文件而非注册表）。

## 1. 核心功能清单

### F1 统一哈希算法抽象（算法注册表）
- **目的**：以单一接口表达 N 种哈希算法，调用方（引擎、UI）不感知具体算法差异；新增算法只改注册表。
- **第一性原理依据**：类型擦除/统一接口消除 N×M 的调用方耦合，符合"一个变化点"原则（单一职责）。
- **落地标注**：
  - **可独立落地**：纯函数/纯接口层面（Python 下为 `hashlib` 统一封装 + 算法注册表；Rust 下为 trait/enum）。不依赖具体 UI 或并发模型。
  - **需架构调整**：原报告的 C-ABI+DLL 插件机制**不适用**本项目（自包含工具不需要运行时加载算法 DLL）；改用编译期注册表即可。

### F2 `is_secure` 算法安全分类
- **目的**：标记算法是否为加密安全哈希（SHA/BLAKE3 等安全；CRC/XXH/MD5/eD2k/QuickXor 等不安全），UI 据此对"不安全命中"给出橙色警示或灰显。
- **第一性原理依据**：可信边界原则——工具须防止用户把非安全哈希误用于完整性/安全断言，避免"看起来校验了其实没校验"的误导。
- **落地标注**：
  - **可独立落地**：算法元数据（布尔标志），纯数据，与计算逻辑解耦。
  - **需架构调整**：需联动 UI 四态配色（见 F7）与校验结果判定（见 F5）。

### F3 单次读取、多算法同算（核心性能结构）
- **目的**：对一个文件，读一次字节流，所有选中算法在同一遍内被 `update`，一次算完多个哈希。
- **第一性原理依据**：只读一遍（IO 是瓶颈），消除重复读盘开销；N 个算法的边际成本趋近于一次读 + N 次 CPU 哈希。
- **落地标注**：
  - **可独立落地**：流式分块读取 + 多上下文 `update` 是语言无关算法结构。
  - **需架构调整**：当前 `src/hash_worker.py` 是"单算法 × 单文件"模型（每次一个 `algorithm`），**尚未实现该结构**，需重构为"多算法 × 单文件"并行 update；这是性能第一杠杆，务必保留。

### F4 内存背压与有界并发
- **目的**：限制同时在途数据块数量（如 ≤512 块 ≈ 1GB 上限），批量文件不爆内存。
- **第一性原理依据**：资源有限原则——并发度必须受内存上限约束，否则批量任务 OOM 崩溃。
- **落地标注**：
  - **可独立落地**：有界信号量/有界队列是通用并发原语（Python `asyncio.Semaphore` / `queue`；Rust `tokio::sync::Semaphore` / 有界 channel）。
  - **需架构调整**：原报告 Win32 线程池（`PTP_IO`/`PTP_WORK`）全平台重写；本项目应改为异步 IO + 工作线程/进程池，块处理完才放行下一块。

### F5 校验文件解析与自动比对
- **目的**：导入 `*.sha256`/`*.sfv`/`*.hash` 等校验文件后，自动嗅探格式、解析出 (文件名, 哈希)，与本工具算出的哈希逐个比对，得出 match/mismatch 状态。
- **第一性原理依据**：格式嗅探优于格式选择（用户不应被要求预先知道格式）；自动比对降低手动核对错误。
- **落地标注**：
  - **可独立落地**：解析逻辑为纯文本处理（hex / base64 / sfv 三格式正则嗅探 + `#`/`;` 注释 + BOM 跳过 + 单哈希粘贴比对特例），与计算引擎解耦。
  - **需架构调整**：本项目已有 `expectedHash`（用户粘贴单哈希），应扩展为支持"导入校验文件 → 按行匹配文件名"，而非仅全局单哈希。

### F6 引擎 / 界面分离（事件订阅模型）
- **目的**：哈希引擎为纯计算模块（无 UI 依赖、可单测）；UI 经事件总线订阅进度与结果，发布"开始/取消/暂停"指令。
- **第一性原理依据**：关注点分离——计算正确性不依赖渲染；同一引擎可服务多种界面（当前 PyQt 与 Tauri 前端并存时尤为重要）。
- **落地标注**：
  - **可独立落地**：定义清晰的引擎输入（文件列表 + 算法集合 + 选项）与输出（进度事件 + 结果事件）契约。
  - **需架构调整**：当前 `hash_worker.py` 直接 `pyqtSignal` 耦合 PyQt；若要服务 Tauri 前端，需把信号改为与框架无关的事件/回调，或由中间层桥接。

### F7 四态语义配色（结果状态机）
- **目的**：结果区/列表以四态区分——match(绿) / mismatch(红) / insecure(橙，由 F2 驱动) / error(红)，让用户一眼判断。
- **第一性原理依据**：状态可区分原则——视觉编码须与语义一一对应，降低误读。
- **落地标注**：
  - **可独立落地**：四态状态机 + 配色语义（绿/红/橙/红），纯前端展示，与报告配色默认值一致。
  - **需架构调整**：当前 `file_list.py` 已有 pending/success/mismatch/error + 浅绿/浅红/浅橙，但**缺 insecure 态**（MD5/CRC 命中无视觉区分），需补；且应迁移到主题变量体系（`--warning` 已定义）。

### F8 设置集中与持久化
- **目的**：集中管理算法开关、展示偏好（大写/等宽）、导出格式、外部声誉同意等，跨会话保留。
- **第一性原理依据**：配置单一可信源原则——避免散落各处的 magic value。
- **落地标注**：
  - **可独立落地**：本项目 `config.py` 已实现 JSON 配置文件持久化（对应报告"弃用注册表"），已满足。
  - **需架构调整**：需扩充字段以覆盖 F2/F5/F9 的选项（算法开关、导出格式、VirusTotal 同意）。

### F9 导出校验文件（多格式）
- **目的**：将计算结果导出为 `*.sha256`(hex) / `*.sfv` / 等格式，含大写、LF、双空格、正斜杠、日期横幅等可选项。
- **第一性原理依据**：互操作原则——工具产出须能被其他工具（含 OpenHashTab 本身）回读，形成闭环。
- **落地标注**：
  - **可独立落地**：纯文本序列化，与计算解耦。
  - **需架构调整**：当前 `exporter.py` 需核对是否已覆盖 hex/sfv 及上述格式选项。

### F10 外部声誉联动（VirusTotal，可选、默认关）
- **目的**：将哈希送外部声誉库一键比对，识别已知恶意样本。
- **第一性原理依据**：纵深防御——本地哈希只能验证完整性，声誉库补充"是否已知恶意"的维度；但隐私优先（只传哈希不传文件）。
- **落地标注**：
  - **可独立落地**：可选模块，网络调用独立封装。
  - **需架构调整**：必须默认关闭 + 显式同意 TOS（原报告 `ForceDisableVT` 企业管控思想）；本项目现有隐私立场应保留。

## 3. 建议 MVP 落地顺序

1. F1 + F2：统一算法注册表 + `is_secure` 元数据（低风险、纯数据结构）。
2. F3 + F4：重构 `hash_worker.py` 为"读一次多算法 + 有界并发"（核心性能点）。
3. F5 + F7：校验文件解析 + 四态配色（含补 insecure 态）。
4. F6：引擎/界面解耦契约（若需服务 Tauri 前端）。
5. F9 → F8 → F10（进阶）：导出、设置扩充、VirusTotal（默认关）。
